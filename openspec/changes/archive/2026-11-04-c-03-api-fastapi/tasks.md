## Acceptance criteria

- `GET /api/v1/health` responde `200 {"status":"ok"}` sin tenant — spec `exponer-api-turnos`, escenario "Health check exitoso".
- Toda operación de negocio resuelve un tenant válido o falla con `400 TENANT_NO_RESUELTO` — escenarios de resolución de tenant.
- `POST /api/v1/turnos` crea, persiste y devuelve `201` con estado `CONFIRMADO`, delegando la doble validación en el dominio — escenarios de alta.
- `GET /api/v1/turnos` devuelve solo turnos del tenant — escenarios de listado.
- Conflictos de profesional y sillón → `409` con códigos `SOLAPAMIENTO_PROFESIONAL` / `SOLAPAMIENTO_SILLON` y sin persistir — escenarios de conflicto.
- `TransicionInvalidaError` → `409 TRANSICION_INVALIDA`; validación → `422 VALIDACION`; envelope `{"error":{"code","message"}}` — escenarios de mapeo.
- `src/domain/` sin imports de HTTP, Pydantic, SQLite, repositorios o infraestructura — escenario "Guard de pureza del dominio".
- Suite completa verde con SQLite real y `TestClient`, sin mocks de base — reglas duras 4 y 5.
